GPU技术难点

从任务表现定位约束，连接技术机制、验证指标、解决代价与产业环节。

先确定任务，再判断瓶颈。同一颗 GPU 跑训练、长文档预填充、逐 Token 解码或科学计算时，限制可能落在不同位置；型号表中的峰值只能说明边界，不能替代实际工作负载的测量。

这张难点地图按因果链阅读：任务需要什么 → 哪一层资源受限 → 用户会看到什么 → 用什么指标定位 → 有哪些解决路径及代价。一次优化还可能把瓶颈转移到下一层，例如加大批量提高计算利用率，也会增加显存占用和排队延迟。

下文的症状和情景均为教学判断，不是某款产品的实测结论。已核验的型号规格会单独标明；从通用原理推导的可能影响也会明确标为机制推断。原专题中的 2026 年厂商发布、送样和量产状态未在此全面复核，不作为这张地图的新事实。

有计算单元，却没有足够合适的工作可做

为什么更高的 矩阵算力，未必换来更快的训练或推理？

任务要先被拆成适合并行执行的算子。小批量、形状不合适的矩阵、连续的小算子或串行依赖，都会让计算单元等待；寄存器与共享内存的占用，又会限制同时驻留的工作数量。模型支持某种低精度，也不意味着每个算子都能进入对应的高速计算路径。

因此，理论峰值与端到端速度之间隔着任务形状、执行路径和调度。提高并行度能摊薄启动成本，但批量扩大后还要承担更大的工作集与排队时间。占用率也只是诊断线索，不能把占用率提高的百分比直接当成性能增幅。

任务中会看见什么

  • 同一模型的小批量吞吐较低，批量增加后单位请求开销下降。
  • GPU 时间线上存在空隙，或大量很短的 kernel 夹杂频繁同步。
  • 更换计算峰值更高的设备后，端到端耗时改善有限。

用什么指标验证

  • 固定模型、精度与输入形状下的迭代时间或 Token/s，同时记录首 Token 与尾延迟。
  • 算子时间占比、Tensor 执行路径、并行计算组活动情况（NVIDIA称SM）与 kernel 启动间隙。
  • 寄存器/共享内存用量、驻留限制与分支或同步等待；不把单一 GPU 利用率读数当作答案。

任务的活跃数据，超过可用显存

模型权重明明能装下，为什么长上下文或增加并发后仍然失败？

任务需要同时驻留的不只是权重。训练还有激活、梯度和优化器状态；自回归推理还有随上下文与活跃请求增长的 KV Cache，以及工作区、运行时保留和内存管理开销。标称容量不是全部可供模型自由使用的空间。

容量不足会迫使任务缩小批量、切分到多卡，或把部分数据移到主机内存。扩容解决的是能否容纳工作集；如果每一步仍要搬运大量数据，迁移链路和显存带宽会继续限制速度，不能把更多 GB 直接换算成更多 Token/s。

任务中会看见什么

  • 加载能成功，但更长输入、更多并发或训练反向阶段出现显存不足。
  • 为容纳任务降低批量后，吞吐下降或排队增加。
  • 开启主机卸载后任务能够运行，但延迟出现明显波动。

用什么指标验证

  • 峰值已分配与已保留显存，并按权重、状态/KV、激活和工作区拆分。
  • 可服务的上下文长度与并发组合，以及该组合下的延迟和吞吐。
  • 内存碎片、KV 淘汰/命中、主机卸载流量与迁移时间。

数据搬得比计算单元消耗得慢

显存没有满，为什么计算单元仍然在等数据？

某些任务每完成一份有效计算，就要从片外显存读取或写回较多字节。如果数据复用不足，执行时间会更多地受搬运限制。逐 Token 解码在较小批量下可能呈现这种特征；它是工作负载判断，不能推广为所有模型、批量和解码实现的固定结论。

理论带宽来自接口的物理上限；实际访问还受连续性、缓存、冗余流量和读写组合影响。程序申请的有效字节与硬件实际搬运的字节也不同。减少一次不必要的显存往返，往往同时节省时间、容量压力和能量。

任务中会看见什么

  • 显存容量仍有余量，但增加计算峰值难以明显缩短热点算子时间。
  • 访问不连续或中间张量频繁写回时，带宽效率较差。
  • 分块、融合或复用缓存后，速度改善大于增加算术操作数带来的影响。

用什么指标验证

  • 热点算子的有效读写字节/时间，并与硬件 DRAM 实际流量对照。
  • 每字节对应的有效计算量、缓存命中情况和访存等待。
  • 固定输入与批量下的 Token/s、Token/J；比较带宽时统一 GB/s 与 GiB/s、单堆栈与整设备口径。

分块、缓存复用与 IO 感知的算子实现减少重复片外读写；FlashAttention 是这一思路的已有算法例子。受片上存储与形状约束，需要实现和验证；收益随任务变化。
改善数据布局并合并访问，避免不必要的中间张量让实际传输中更多字节服务于有效工作。格式转换可能抵消收益，必须检查端到端时间。
采用更高有效带宽的显存方案，或在延迟允许时增大批量扩大数据供给，或让权重读取服务于更多请求。显存与封装成本、功耗和容量需求增加；延迟目标可能限制批量。

加了更多 GPU，却把时间花在交换数据

为什么单卡快，扩到多卡或跨节点后却难以按卡数加速？

分布式训练需要同步状态或梯度，模型分片推理也会在计算阶段之间交换数据。把任务切得更细，可以降低每卡工作量，却可能增加通信次数或比例；小消息还会受到启动与同步延迟影响。远端显存因此不能按本地显存的代价访问。

实际通信路径由设备互连、拓扑、网络和软件配置共同决定。链路标称速率不等于某次集合通信的有效吞吐；同一批卡也可能因放置位置或直通路径不同而表现不同。是否能将通信隐藏在计算背后，同样取决于数据依赖和并行策略。

任务中会看见什么

  • 增加 GPU 后总吞吐有改善，但每卡吞吐下降，甚至整体变慢。
  • 时间线中集合通信或同步等待占比上升。
  • 同卡数的不同节点或拓扑组合，完成时间差异明显。

用什么指标验证

  • 固定总任务或固定每卡任务下的扩展效率，明确采用哪种口径。
  • 通信时间、消息大小分布、计算/通信重叠比例与慢设备等待。
  • GPU 间和 GPU 到网卡的实际带宽/延迟、P2P 可达性、拓扑及网络拥塞。

合并适合的消息，并将可重叠通信与计算流水化摊薄通信启动成本，减少显露在关键路径上的等待。需要额外缓冲和正确的依赖管理，可能延迟部分数据的发送。

能把芯片连起来，还要能稳定产出合格模组

为什么有 GPU 裸片、有 HBM 堆栈，仍不等于有可交付加速器？

任务对容量和带宽的要求，会转化为更多存储裸片、堆栈与高密度连接。HBM 层内堆叠和 GPU+HBM 的系统级封装是不同工艺链，最终必须一起通过连接、热与功能验证；任何阶段的缺陷都可能把已投入的昂贵部件变成损失。

因此，先进封装需要同时考虑连接密度、材料形变、可测试性和生产节拍。已知良品裸片可以降低把坏芯片装入系统的风险，却不能证明后续键合和组装不会产生新缺陷。更多中间测试能提前拦截问题，也会增加测试时间与制造成本。

任务中会看见什么

  • 器件样品达到目标，但合格模组的稳定产出或成本仍不理想。
  • 单部件测试通过，组装后的带宽、连接或热可靠性测试失败。
  • 产出受限于堆叠、基板、系统封装或测试中的某一道工序。

用什么指标验证

  • 分别记录裸片、堆栈、组装和最终测试的良率，写明分母与筛选阶段。
  • 每小时合格产出、设备节拍、测试覆盖/时间、返工与报废成本。
  • 每个合格模组的成本及热循环/连接可靠性；不使用假设良率乘积代替真实产线数据。

协同选择中介层、RDL、局部硅桥等连接结构在连接密度、封装尺寸与制造条件间寻找可行方案。需要重新验证信号、电源、机械与热设计，不能只按工艺名称排序。
优化堆叠、键合、材料与热路径降低连接缺陷和热机械压力，改善合格产出。新工艺需要设备、过程控制与可靠性验证；研究路线不等于量产能力。

瞬时能跑得快，供电与热量未必允许长期维持

为什么同一任务刚启动很快，持续运行后却降速？

持续计算与访存需要电源不断供能，并把热量经封装、散热界面和系统冷却排出。低压大电流带来供电路径与转换损耗；局部热点和材料界面热阻，会使机房空气温度之外的条件也影响器件温度。

功率限制、温度控制或系统电源约束都可能降低运行频率。它们需要与任务剖析一起解释：低功耗可能来自等待数据，也可能来自限频；高功耗则不保证高有效吞吐。模块 TDP、实际模块功率和整机/冷却能耗属于不同口径。

任务中会看见什么

  • 长时间运行的频率与吞吐低于短时测量，且伴随功率或温度限制事件。
  • 同一节点内设备表现不齐，需要排查风道、接触与冷却分布。
  • 扩大机柜配置后，电力或冷却条件先于 GPU 数量成为部署约束。

用什么指标验证

  • 在相同采样时间线上记录吞吐、频率、实际功率、温度和限频原因。
  • 区分模块功率上限、模块实耗、整机与设施用电，评估 Token/J 或任务/J。
  • 持续稳定阶段的性能、供电余量和冷却条件，而非只测启动时峰值。

硬件提供了能力，软件还要正确地用起来

为什么规格相近的设备，迁移同一模型却有不同的工程成本与表现？

业务性能依赖驱动、编译器、框架、算子库、通信库和模型实现共同覆盖目标硬件。硬件支持的精度或指令，需要软件选择正确的执行路径；缺少适配时，可能出现不支持、回退、额外转换或调优不足。

部署又要求结果正确、版本可复现和升级可控。低精度、融合和近存计算等路径都要检查数值与语义；驱动及运行时之间的兼容也有边界。因而比较生态，应看完成既定任务所需的适配、验证与维护工作，而不是只数支持了多少名称。

任务中会看见什么

  • 程序能够启动，但热点算子没有走预期的加速路径。
  • 迁移设备或升级软件后，出现不支持的算子、编译问题或性能回退。
  • 速度提高后，任务准确性、收敛或结果一致性未达到要求。

用什么指标验证

  • 目标模型与形状的算子覆盖、回退/转换时间和端到端耗时。
  • 在明确准确性标准下的吞吐、延迟与能耗。
  • 可复现的软硬件版本组合、适配工时、构建部署时间与升级回归。

跑出样品性能之后，还要持续交付正确结果

为什么系统验收与长期运维，也是有效算力的一部分？

长期训练与在线服务需要整套系统在目标条件下稳定工作。器件通过部件测试，并不替代服务器互连、供电、冷却与应用验证；内存错误、链路异常或恢复操作都可能让正在运行的任务停顿。可靠性机制可以限制部分故障的影响，但其支持范围与恢复条件必须按设备和软件查证。

交付还要求 GPU、显存、封装、板级系统与设施按时汇合，并能维护、替换和恢复。有效算力因此应按符合质量要求的结果来衡量：验收未通过、停机或需要重跑的时间，不能算作已交付的业务吞吐。这个因果框架不能用于推定某家公司当前缺货或某型号的故障率。

任务中会看见什么

  • 短测试通过，长作业却出现错误、重置、重跑或不可解释的中断。
  • 设备已经到货，但系统验证、网络或电力冷却条件尚未完成。
  • 实验吞吐较高，计入维护、恢复和失败任务后，实际服务能力偏低。

用什么指标验证

  • 任务成功率、满足质量与延迟要求的有效吞吐、可用时间。
  • 可纠正/不可纠正错误及恢复事件，结合厂商定义解释，不把计数直接等同于故障率。
  • 检查点与恢复耗时、重跑工作量、整机验收通过率和各交付环节的就绪状态。

把难点放回工作负载

以下是定性教学场景，不是某型号的性能测试。

教学情景：长文档问答，增加上下文或并发后装不下

  • 假设权重加载成功，短请求运行正常。
  • 假设更长的输入或更多活跃请求导致显存分配失败，或触发卸载。

先检查容量链：权重之外的 KV 与临时工作集可能超过余量。若卸载后能运行但变慢，再检查迁移流量与链路；不能仅凭显存不足就判断计算单元不够，也不能把换大显存后的吞吐改善当成带宽实测。

先做什么检查

  • 固定模型、精度和请求长度，逐项记录峰值显存及 KV/工作区占用。
  • 在不同上下文与并发组合下观察失败边界、排队和延迟。
  • 确认是否发生主机卸载，记录复制流量与等待时间。
容量瓶颈 →分层存储 →

教学情景：预填充较顺畅，逐 Token 输出仍然慢

  • 假设同一模型的预填充与解码阶段表现不同。
  • 假设低并发时每 Token 延迟偏高，适度合并请求后总吞吐改善。

先把阶段分开：预填充能够提供较大矩阵工作，解码的矩阵形状、数据复用和启动成本不同。低批量解码可能受显存流量限制，也可能由小算子启动或依赖主导。必须同时看数据流与执行时间线；这是定性假设，不是所有模型的固定规律。

先做什么检查

  • 分别统计首 Token 时间、每 Token 时间和两阶段的热点算子。
  • 比较 DRAM 流量、Tensor 活动与 kernel 间隙，辨认等待来自哪里。
  • 在同一延迟目标下改变批量，记录吞吐、显存和排队代价。
计算利用 →显存带宽 →缓存与 IO 优化 →

教学情景：分布式训练增加节点，速度却没有随之增长

  • 假设单节点结果稳定，跨节点后每轮等待变长。
  • 假设增加卡数后，每卡计算量下降，而同步时间占比上升。

这符合通信或同步成为关键路径的机制，也需要排除输入管道、负载不均和异常设备。先明确是固定总任务还是固定每卡任务，再比较；否则扩展效率的分母不同，结论没有可比性。

先做什么检查

  • 记录每轮计算、集合通信、输入与等待时间。
  • 核对实际拓扑、P2P/GPU 到网卡路径，测量对应消息规模的通信。
  • 比较不同并行切分及节点放置，观察通信是否可被计算覆盖。
互连与通信 →系统层级 →

教学情景：短时测试很快，持续服务后变慢或重跑

  • 假设任务形状保持不变，运行一段时间后吞吐下降。
  • 假设部分作业出现恢复事件，或设备之间持续表现不齐。

先用同步记录区分功率/热限制、输入变化和故障恢复。若频率下降同时出现限频原因，可沿供电与冷却链检查；若有错误或重置，则沿可靠性链分析。不能只用温度高或一条错误日志解释全部慢请求。

先做什么检查

  • 将吞吐、频率、功率、温度和限制事件放到同一时间线。
  • 核对错误类别、发生设备及恢复动作，计算丢失和重跑的工作量。
  • 比较稳定阶段的有效吞吐与任务能耗，并复核整机验收条件。
