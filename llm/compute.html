CED：长输入与逐 token 生成的不同路径

逐步图解 · 教学示意

把长输入与逐 token 生成分开

观察输入经过哪些层，尾部为什么仍需处理，以及生成时使用哪些部分。

图示的简化与适用范围

采用 V4.1 公开结构作流程简化；图示不模拟时延，有限重放存在近似，生产缓存调度未完整公开。

核验日期：2026-11-14。范围是官方论文与参考实现的架构解释，不是模型实测。V4.1 架构解释核对官方技术报告正文。下文层号统一从1开始；源码配置数组从0开始。

先固定问题：读输入与写输出是两种工作

普通 causal decoder 中，prompt 的每个位置都过全部 L 层。第 l 层通常从本层输入状态生成自己的 K/V：K_l = H_l W_lK, V_l = H_l W_lV；新 token 的 Q 读取这一层缓存的历史 K/V，得到新隐状态，再过 FFN。prefill 把很多输入位置并行处理；decode 一次追加一个或一小批位置，反复读历史缓存。过去位置已经算出的状态由 KV 缓存保存，并不会每产生一个字就重跑全部历史。

分开看两笔账：① 每个位置过几层、激活多少 FFN/专家；② 历史里保存和读取多少 KV，索引器又扫描多少位置。MoE 省 FFN 激活量，稀疏注意力省远程访问，压缩 KV 省存储，它们作用于不同环节。

普通分离K/V的GQA，可用 M_KV ≈ N × L × 2 × n_kv_heads × head_dim × bytes_per_scalar 理解缓存线性增长。DeepSeek共享KV向量同时作为key与value，不能把这个普通公式中的“×2”原封不动套进其缓存账本。

V4：先把时间轴压短，再决定看哪些块

V4论文§2.3.1—§2.3.3 ↗同时采用CSA与HCA，并加一条保留最近细节的滑窗分支。它并没有把整个序列都变成512个token。

原始历史位置 1 ... N
   ├─最近 W 个位置：未压缩 SWA KV ─────────────────┐
   ├─CSA层：压为 N/m 个槽 → 轻量索引打分 → Top-k ─┤→ 本层Q做注意力
   └─HCA层：压为 N/m' 个槽 → 全部压缩槽参与注意力 ─┘

CSA、HCA是交替层的两种全局分支；不是同一层必须同时运行上图两条全局分支。每层都有本层local SWA。

  • CSA不是DSA的同义词。 DSA是索引器挑选少量历史位置的方法；V4的CSA先在序列维度压缩KV，再把DSA应用到压缩槽上。减少读取的槽数，与减少必须保存的总槽数，是两件事。
  • 压缩不是简单截断或均值。 可用 c_j = Σ_i α_{ji} ⊙ v_i 理解，α由可训练门控按通道加权产生。V4 CSA每个输出槽汇合相邻、重叠的2m个源条目，输出长度仍约N/m；HCA用更大、非重叠块。源码的Compressor明确实现门控池化和未满一块时的尾状态。
  • HCA不再Top-k。 它把更长一段历史压成一个槽，然后读全部压缩槽。Flash配置CSA m=4、k=512；HCA m'=128；W=128。Pro的CSA k=1024，别把Flash与Pro配置混用。见V4论文§4.2.1 ↗。
  • 以Flash的N=1,000,000为教学例：CSA索引器仍面对约250,000个压缩候选，而重型主注意力最多读512个远程槽及128个local槽；HCA则读约7,813个全局压缩槽及local槽。这个例子说明，“主注意力只看固定k”不等于全部注意力计算对N为常数，轻量索引仍可能随长度增长。

粗略地说，CSA一层每个query的全局部分是 index_cost(N/m) + core_attention_cost(k)；HCA是 core_attention_cost(N/m')，再分别加local W与投影/归一化开销。prefill还要对许多query重复做索引，不能由“decode主核固定k”推导prefill线性复杂度。

代价也很具体：远处原始token被合并，罕见细节可能损失；相关槽若没进Top-k，主注意力就读不到。local SWA补救的是最近一段精确信息，不保证任意远处的数字、否定词和引用都完整保存。

V4.1的CED：让长输入减少逐位置执行完整网络的计算

直接证据：V4.1技术报告§2.2，PDF第9页 ↗。模型为40层：下20层是causal encoder，上20层是decoder；两部分都保持因果性，encoder不是传统seq2seq的双向encoder。

一般CED公式把decoder全局KV的数据来源改成encoder最终状态E，而不是本decoder层隐状态：

传统：每层本层状态 H_l → 自己的global K/V
CED：token → E1...E20 → E_final → 投影得到decoder global KV
                              └→ D21...D40 → logits

一般设计：C_l = E_final W_lKV，Z_l = E_final W_lZ，l > 20

这里“同一个encoder最终状态”不自动等于“所有层同一组KV”。上式允许各个decoder Full层有自己的投影。实际V4.1再叠加CSA2层间共享后，decoder只有第21层产生一组global KV；第22—40层共享这组main KV和对应indexer K。 每个decoder层仍有自己的Q、自己的local SWA KV、输出投影和FFN，绝不是复制第21层输出。

实际共享关系由官方config.json ↗直接给出：

位置实际做什么
encoder第1—2层只有SWA
encoder第3、9、15层三个独立Full KV源，每个2:1压缩；中间层复用最近源
decoder第21层从E_final产生一组不做序列压缩的global KV（m=1），并运行全局索引
decoder第25、29、33、37层用本层indexer Q对共享indexer K重新选Top-512
其余decoder层复用最近一次Top-512选择，仍用本层Q对这些KV重新计算注意力

冷prefill： 全prompt先过20层encoder，得到全prompt的E_final及decoder需要的global KV。大部分位置到这里结束；但最后W=128个prompt位置仍要过20层decoder，建立每层自己的local SWA状态，并得到产生首个输出所需的末位置logits。所以不能说“decoder读prompt完全零计算”。

decode： 每个新产生的token仍依次过20层encoder和20层decoder，追加encoder与共享decoder global KV，并更新各层滑窗。旧prompt的encoder结果由缓存复用，不是每次生成token重跑整段encoder。

8B prefill/16B decode对应这条不对称主干路径：绝大多数长prompt token只跑半个主干，生成token跑全主干；不是把同一计算任务 magically 用一半参数完成，也不是8B权重就能部署。尾部重放、KV投影、索引、视觉编码、通信均不应忽略。

论文写的层工作量近似为 NL/2 + WL/2，相对完整prefill的NL。它是token×层级别的解释，不是包括注意力索引在内的严格全部FLOPs公式。教学例N=32,768、L=40、W=128，比例约0.502；若prompt短于128，尾部decoder工作已占很大部分，不能许诺首token时延一定减半。

CSA2：共享“记忆本体”与共享“去哪找”可以分开

证据：V4.1报告§2.3.1，第10页 ↗，源码Attention与SharedAttentionRuntime ↗。

模式新造main KV/indexer K本层重新打分选Top-k本层Q、SWA、主注意力、FFN
Full是是都要算
Reindex否，复用此前Full的KV/K是都要算
Reuse否否，复用最新indices都要算

KV共享减少存储；indices共享减少索引计算。这两个收益不等价。Reuse仍可对同一候选集合赋予不同注意力权重；但不能在本层选择之前没入选的新位置。

V4.1用纯CSA2替代V4的CSA/HCA交替，并把压缩器简化为无重叠、无压缩绝对位置偏置；indexer K从main KV投影，不再单独从hidden states走一条压缩路径。

分层索引避免重复扫描全部历史。 第21层先扫描全部因果可见位置，按每8个位置一块取块内最高分，选2,048块，组成最多16,384位置的候选池。后续Reindex层只在这个池里选自己的512个位置。这样是“第一次扫描仍随N增长，后续几次扫描上限固定”，不是整个模型与上下文长度彻底无关。若最初把相关块剪掉，后续重新打分也救不回来。候选限制在后训练中模拟；见§2.3.2，第11—12页 ↗。

FP4 KV：省的是持久记忆的字节，不是把所有矩阵算子改成FP4

证据：V4.1报告§2.4.4，第14页 ↗，kernel.py的fp4_act_quant ↗。

main KV用E2M1，每16个通道共用一个8bit E4M3 scale，近似4.5bit/数，不是完全没有元数据的4bit。读入注意力前反量化，因而这种格式的主要作用是减少存储和搬运，不要求该格式原生矩阵乘法。RoPE后量化；RoPE与非RoPE部分同格式。作者在后训练加QAT。对量化较敏感的local SWA KV仍保留FP8。

890 bytes/token可以从配置复算，不必背宣传数字：

  • 四个global源的槽数因子是3/2 + 1 = 2.5：encoder三个源各N/2，decoder一个源N。
  • 每个main KV槽512维，字节为512×0.5 + 512/16×1 = 288。
  • 每个indexer K槽128维，FP4加每32维一个8bit scale：128×0.5 + 128/32×1 = 68。
  • 合计2.5 × (288 + 68) = 890 bytes / 原始token。

这是本节按官方代码/格式的独立算术复核，不是实测显存。若N按十进制100万算，global KV约0.89GB/序列；不含模型权重、local SWA、尾块、元数据、工作区、并行复制和请求批量。1/4指global KV相对V4-Flash，不是整机显存或整任务费用变1/4。

Bounded Replay：少存local状态，恢复时接受近似

证据：V4.1报告§3.2.1，第19页 ↗、§3.2.2，第20页 ↗。

单层SWA只看W个近邻，但层层堆叠后的依赖范围扩大。若没有local缓存，要精确恢复L层的最后W个local状态，可能需重算约L×W个历史位置；不能因为“滑窗128”就说完整模型只依赖128个token。作者只重放最后W个位置，并把重放段开始之前的local注意力截掉：SWA_allowed(i) = [max(s, i-W+1), i]，s是重放起点。

这里有两种不同场景：

  1. Encoder SWA Bounded Replay是缓存缺失恢复。 global前缀缓存仍在、encoder local SWA状态已经过期时，重放已缓存前缀末128个token，再接新的工具结果/用户输入。重放区只重建SWA，复用旧global KV，不重算和覆盖它；未缓存新后缀正常生成global与local KV。并非重新编码整个长前缀。
  2. Decoder SWA Bounded Replay是CED prefill收尾。 每次prefill，把prompt最后128个位置的encoder输出过20层decoder，以初始化各decoder层local状态；这些decoder local状态供随后的decode使用，不写长效前缀缓存。它是“跳过绝大多数prompt的decoder”能够成立的配套处理。

冷prefill已算出尾部encoder输出。暖缓存情况下，短后缀之前那部分尾部encoder输出如何在各引擎中保留/调度，论文没有给出足以复现的完整服务端实现；不要擅自承诺某种引擎完全不额外重算encoder。可以明确证明的是：没有每生成一个token重跑整个encoder前缀；encoder local缓存缺失时有界重放；decoder不能跳过尾部状态初始化。

代价是数学近似，不是无损缓存格式。 作者明确说，重放的前缀状态是近似的，后来新后缀算出的global/local KV可能依赖命中边界；因此同一完整prompt从不同cache-hit位置继续，不保证中间状态逐位相同。作者在后训练模拟decoder重放，报告已测场景质量损失小，但这里未找到一个逐项量化“所有边界退化上限”的消融表。不能把“negligible”写成已独立证明普遍无损。

为什么persistent KV可约降到1/8，却不等于HBM再除8

V4.1论文中的两项口径不同：global runtime KV常驻HBM，约V4-Flash的1/4；persistent KV是SSD/host上用于复用的长效缓存，约1/8。作者原部署persistent容量约一半是global、一半是SWA。新设计把SWA移出长效缓存，只给活跃会话的encoder local状态一个分钟级DRAM池；global仍长效保留。去掉约一半 × 剩下global压成1/4 ≈ 原persistent的1/8。

报告说其DRAM池约用每机10% host内存，global缓存保留至少72小时；这是作者部署配置，不能改写为所有第三方托管、所有API请求均承诺同样命中时效。V4论文§3.5.2另谈“存所有token的SWA会是global约8倍”；那是另一存储策略，不要与V4.1描述的实际检查点容量“一半”混算。

证据强度与复现边界

  • V4.1最小推理README ↗明确它是可读参考实现，不是生产服务引擎。核验时Transformer.forward对整个传入prompt循环全部40层，没有CED“只处理decoder尾部”的生产调度；源码可证明共享和数值路径，不能直接拿它跑出的时延验证论文的prefill减半。
  • 同一参考代码的fp4_act_quant(..., inplace=True)把量化后反量化值写回原张量，便于复现数值效果；不代表该运行路径真的按890 B/token打包所有main KV。Indexer也先构造分数再mask候选，不能把它当已展示生产级索引吞吐优势的证据。
  • V4“1M上下文时Pro单tokenFLOPs约V3.2的27%、KV约10%”是特定型号/长度条件；V4.1图2还把BF16、FP8、FP4操作分别按1、0.5、0.25加权。加权FLOPs、物理指令数、首token延迟、单用户输出速率、整服务吞吐不是同一指标。
  • V4.1报告§6，第37页 ↗明确承认：CSA2误选和SWA近似重建在未覆盖边界可能退化。研究员应分别做cold/warm前缀、不同命中边界、极短工具返回、长文多事实/否定/精确引用测试；同时记录任务成功率、人工接管率、p50/p95时延、缓存/工具/输出费用。

MoE：选择计算与权重驻留

逐步图解 · 教学示意

路由、专家计算与合并

切换 token 特征，观察被选专家、共享专家和保留的权重。

图示的简化与适用范围

8 个路由专家选 2 个，加 1 个共享专家，是教学配置；不对应 K3 等真实模型规模或职业分工。

核验截至2026-11-14。这里讲机制，不做模型排名。证据分为作者论文、官方演示代码、推理框架实现，以及明确标作教学假设的算术。代码读通不等于完成训练复现；没有把某篇研究自动等同所有商业API的实现。

先回答：加参数，究竟加的是什么？

变化每个token多做什么增加的主要资源不能直接推出什么
Dense FFN加宽/加深执行更多矩阵计算FLOPs、权重、激活、带宽效果必然按参数量增长
MoE增加专家数E、保持每token选k不变从更大的参数库里选择少量MLP执行总权重、router、专家分布和通信；专家计算不按E同比增长总参数越大，每token算力同比越大；只需装入激活参数就能部署
MoE提高k同一token执行更多专家并组合FLOPs、激活搬运、通信不重新训练/校准也会单调变强
增大n-gram条件记忆表仍只取少量向量，表中可学习槽位变多参数存储、随机访问、训练更新、CPU↔GPU链路新增51B查表参数等于新增51B矩阵计算；可以免费无限扩容
增大KV cache保存更多本次请求的历史中间状态随序列/并发变化的运行时内存模型学到了更多固定知识；模型参数变多

“计算容量”和“查表容量”都能扩展模型表达能力，但资源账不同。MoE是conditional computation：挑哪些函数来算；Engram/n-gram embedding是conditional memory：挑哪些训练过的向量来读。后者仍需要门控、投影、卷积，绝非零计算。稀疏MoE已在2017年论文中系统展示，共享专家/细粒度专家见2024年DeepSeekMoE；不能全部算作2026原创。稀疏MoE论文 ↗、DeepSeekMoE ↗

MoE的一次前向：router不是一个能“理解行业”的总经理

查看结构连接（文字版）
  • 本层token表示 h → Router计算所有专家分数
  • Router计算所有专家分数 → 选中top-k专家及组合权重
  • 选中top-k专家及组合权重 → 把token向量发往专家所在设备
  • 把token向量发往专家所在设备 → 专家MLP 1
  • 把token向量发往专家所在设备 → 专家MLP 7
  • 专家MLP 1 → 结果回传并按权重相加
  • 专家MLP 7 → 结果回传并按权重相加
  • 本层token表示 h → 共享专家MLP：通常每token都计算
  • 共享专家MLP：通常每token都计算 → 合并输出与残差
  • 结果回传并按权重相加 → 合并输出与残差

一个专家通常是某层里的FFN/MLP参数块，并非一套完整模型；一篇财报的不同token、不同层可以走不同专家组合。训练可能产生某些偏好，但不能仅凭名称宣称“这个专家只懂金融”。

教学简式（省略残差和具体归一化）：

MoE(h) = Shared(h) + Σ[i∈TopK(router(h))] gate_i(h) × Expert_i(h)

  1. attention等前序运算先形成当前层的hidden state h。
  2. router通常是一个轻量线性投影再经softmax或sigmoid，算出token与各专家的匹配分数。
  3. 取top-k，将token向量分派到选中专家；专家执行矩阵运算。
  4. 按gate把输出相加。共享专家可承担公共模式，避免每个路由专家重复学习同样的基础变换；有些实现再给共享通路加gate，不能把一种做法套到所有模型。
  5. 接回残差流，进入下一子层。下层可重新路由。

可直接对照DeepSeek官方代码：Gate.forward保留原始匹配分数，用偏置后的分数决定选择，再用原始分数产生混合权重；MoE.forward只运行本设备被命中的专家，另算共享MLP并归并结果。官方教学推理代码这里采用all_reduce合并，不等于生产专家并行一定采用同样通信拓扑。 固定版本代码：Gate/MoE ↗

为什么负载均衡影响模型质量，也影响吞吐

若多数token挤进几个专家，会出现热门专家过载、其他专家缺训练信号，设备相互等候。常见方法是用辅助损失约束专家使用分布；约束过强又会干扰任务本身学习。Switch Transformer ↗

DeepSeek-V3的思路是反馈调路由偏置：过载专家的选择偏置往下调，欠载专家往上调；偏置用于选谁，混合输出仍按原匹配分数。它仍保留了很小的序列级辅助项，所以“auxiliary-loss-free”不应解释成训练中绝无任何均衡辅助损失；节点受限路由也在减少跨节点分散。这是2024/2025已公开路线，不是2026首次发明。 V3 §2.1.2与§4.5 ↗

训练时的均衡也不保证推理时每批都均衡：真实业务域、batch大小及分布会变，生产系统还可能复制热门专家、动态调整部署与通信。这些是运行时优化，不必然意味着模型新架构。

总参、激活参数、权重驻留：用一笔账打通

只看一个MoE层的路由专家部分，设 E个同宽专家，每个P_e参数，每token选择k个：

全部路由专家参数 = E × P_e

单token选中专家参数 = k × P_e

后者可粗看专家矩阵计算的规模，却不是整个模型的总显存或完整FLOPs公式。还需另算attention、共享专家、router、embedding/output head、层数、序列长度及量化格式；模型卡“激活参数”也有具体统计约定。

教学例：64个专家，每个100M参数；每token选2个，另有一个100M共享专家。总专家权重6.5B，单token执行约300M专家参数。若全部BF16保存，裸专家权重约13GB；不能说“激活300M，所以只需0.6GB显存”。未被当前token选中的权重依然属于模型，需要在HBM、主存或其他存储层可取得。

batch会改变实际工作集。在“不同token独立、均匀选专家”的教学假设下，B个token预计触及专家数为：

E × [1 − (1 − k/E)^B]

64专家、top-2、32个token，约触及40.8个；64个token约55.6个。这不是实际router预测，只说明每token稀疏，不代表整批只读两个专家。大batch把许多token聚成专家GEMM有利于利用率，也会增加工作集；小batch和长尾专家可能形成许多很小的GEMM。

专家并行通常把专家权重分散驻留到设备上，传的是token表示和专家输出，而非每次把所有专家权重搬来搬去。粗略忽略去重、分组及拓扑，dispatch与combine流量随 B × k × hidden_dimension × 每元素字节 增长；通信等待可能抵消FLOPs节省。专家权重卸载也能做，但router依赖当前层h，通常不像token确定地址的查表那样，可在前向开始前精确知道所有要取的专家。

跟随 token 地址、主存表、门控和融合，区分查表与推理。

图示的简化与适用范围

哈希槽与门值是教学例；表中是训练向量，不是答案库或用户会话记忆，也不自动更新现实事实。

Engram：熟悉的局部组合，先查一份可学习的“速记”

Engram读取的是训练参数中的向量，不是网上文章、用户历史数据库或可直接展示的事实条目。普通推理时表固定；训练或微调可以更新。静态的是表与地址规则，最终采用多少是上下文相关的。

查看结构连接（文字版）
  • 当前已知token及短后缀 → 仅查表分支：token规范化映射
  • 仅查表分支：token规范化映射 → 2-gram / 3-gram 多头hash地址
  • 2-gram / 3-gram 多头hash地址 → 主机或设备上的可学习embedding表
  • 主机或设备上的可学习embedding表 → 拼接取回向量 e
  • 拼接取回向量 e → Key / Value投影
  • 前序层产生的上下文表示 h → 比较h与Key，计算gate
  • Key / Value投影 → 比较h与Key，计算gate
  • Key / Value投影 → Value
  • 比较h与Key，计算gate → gate乘Value
  • Value → gate乘Value
  • gate乘Value → 轻量因果短卷积及残差融合

以三个示意token New / York / City 为例：到City这个位置，查表分支可以用后缀York City及New York City分别生成地址。这是示意分词，不保证任何实际tokenizer恰好如此切分。 同样的局部token后缀会取到同组参数向量，而前面谈城市、球队或同名实体的上下文不同，会改变gate。

对照官方demo，把步骤逐一读出来

以下基于官方demo固定版本 ↗，不引用生产模型的精确超参。

  1. CompressedTokenizer预先建立原token ID→规范ID映射，使用Unicode、大小写、空白等规范化合并部分表面变体；没有改动主干原始token，也不是把所有同义词压成一个词。
  2. NgramHashMapping把每个位置结束的短n-gram经乘法/XOR及取模映射到若干表。多个hash头是对冲撞桶的多份索引，不是attention的多个Q/K/V头。有碰撞仍可能共享部分向量，不能说无碰撞精确数据库。
  3. MultiHeadEmbedding取出各阶各头的一行并拼接为e，而非扫描整张表。demo中2/3-gram、各8头，每头64维，共1024维，只是演示配置。
  4. Engram.forward从e投影出Key和Value，从当前上下文h取Query；做归一化相似度和sigmoid门控。多分支共享查表/Value，Key与gate按分支变化，避免每条分支都复制整个巨大表。
  5. 门控后的Value经因果depthwise短卷积完善局部交互，再与门控Value相加，最后注入主干残差。

示意公式（单分支）：

z[n,j,t] = hash[n,j](normalized suffix tokens)

e_t = concat[n,j](EmbeddingTable[n,j][z[n,j,t]])

s_t = dot(RMSNorm(h_t), RMSNorm(W_k e_t)) / sqrt(d)

a_t = sigmoid(f(s_t)); u_t = a_t × (W_v e_t)

memory_output_t = u_t + CausalShortConv(u)_t

论文简式用f(s)=s；demo里额外有保号平方根变换（先abs().clamp_min().sqrt()再乘符号），因此这里显式保留f。若逐行复现，必须以指定版本实现为准，不能把以上简式当所有实现数值完全等价。

最重要的代码边界：demo开头说明Attention、MoE和复杂连接机制被省略或mock，尚需生产kernel和分布式优化。它能解释数据流，不能证明生产吞吐、训练结果或某商业端点已按这份demo部署。

为什么能预取，为什么又不是“零时间记忆”

查表地址只依赖已经知道的token，故可在模型到达记忆层之前，把所需小向量取来，与前序层计算重叠。prefill时整段prompt已知；decode时只能在当前输入token确定后预取相应内容，不能提前知道还没生成的未来token。

作者在H800、512条序列、长度100–1024、4B/8B dense主干、第二层插入100B表的实验中，主存卸载吞吐下降约1.9%/2.8%。这是特定吞吐实验，且刻意未混入MoE专家并行，不能外推单用户延迟、任意CPU、所有长上下文或所有batch。论文的O(1)指固定n-gram阶数/头数下地址查找不随整张表容量线性扫描，不是端到端推理耗时永远不变。Engram论文§2、§6.4 ↗

Qwen的n-gram扩容：同一思想族，不是每个细节都照抄

Qwen3.8-Flash-Next公布约125B主干+51B n-gram表，6B每token激活。不能把176B全部称为矩阵计算主干，也不能把51B查表参数解释成51B每token全部执行。官方仓库 ↗

论文§2.3明确使用多头hash及上下文门控，采用一个记忆注入层，并选择Layer2为前一层计算留下预取窗口；它尝试token规范化等变体，但在该训练配方下未得稳定收益。不能把Engram的规范化必选项套到Qwen。 还发现表更大时loss持续下降，而下游准确率有饱和或波动；同参数预算下增加记忆会挤占其他容量，最优分配不是“全部给表”。Qwen技术报告§2.3 ↗

作为实现交叉核对，SGLang中该架构使用内部名qwen4_exp；它服务Qwen3.8-Flash-Next并不表示所有Qwen4产品已经采用相同权重/配置。以下链接固定到2026-11-13代码：

  • Qwen4ExpNGramEmbedding：生成多头n-gram地址、管理表和分片。
  • Qwen4ExpPLELayer.start_prefetch：在独立stream中取行；到需要融合时wait_stream等待，没有取完仍然会阻塞。
  • Qwen4ExpPinnedHostEmbedding与host-table模块：支持pinned主存，以及特定条件的文件/mmap方案。GPU可以通过UVA直接读host表；“在CPU内存”不必然等于“CPU核执行全部查表”。
  • 这份实现也能看到Key/Value投影、归一化gate和短卷积，不是简单把一个字典向量无条件加上去。

主存和互联的账：省HBM，瓶颈可能转移

先算容量：51B表若全部BF16，理想裸权重约102GB；FP8约51GB，另有scale、元数据和缓冲。若主干125B也全部BF16，另需约250GB裸权重。整模型约352GB这个算术不能被“每token激活6B≈12GB”替代。可量化、分片、卸载，但每项都有工程条件和精度代价。

再算每步交通量。教学简式：

读取量 ≈ 同步处理token数 B × 记忆层数 L_m × 每token取出的总维数 d_mem × 每元素字节 b

重复行去重/缓存可降低交通量，随机访问的缓存行、页面与同步开销又可能放大实际成本。用上文demo维度作纯教学：B=512、两个记忆层、d_mem=1024、BF16=2字节，约2MiB；若有效链路32GB/s，仅理想传输约65.5微秒，尚未计随机读延迟、hash、gather、投影、同步和拥塞。这不是任何发布模型的实测。

可隐藏的部分由时间窗决定：

未隐藏等待 ≈ max(0, 查表/搬运耗时 − 可重叠的前序计算耗时)

这是排程直觉，不是可直接拿来预测生产SLA的完整模型。小batch时固定延迟占比可能较大；大batch/高并发时随机主存带宽、PCIe/C2C和NUMA跨socket通路可能拥塞。低精度主干越快，原来能隐藏的搬运也可能重新暴露。

需要同时测：主存实际随机访问带宽、GPU↔CPU有效带宽、hot-row命中、p50/p95查表等待、prefill/decoding分段吞吐、并发下尾时延，以及质量/输出token变化。分离GPU+主存平台上可释放HBM；统一内存平台把表换到“CPU”未必释放物理总容量。SGLang的host-table实现明确讨论了这种差别。host存储设计 ↗

因此可形成产业链研究假设：便宜DRAM、更快CPU-GPU互联、NUMA/预取/缓存软件的价值可能上升；但不能从51B表直接推算新增服务器订单。实际量化、共享缓存、负载、复用与需求量都要进入模型。

五种叫“记忆”的东西，生命周期完全不同

对象存的是什么 / 怎么读取生命周期和Engram的关键区别
Engram / n-gram表训练好的参数向量；局部token确定hash地址，hidden state决定融合强度多请求共享，普通推理不更新不保证人可读、可溯源；不是新用户事实自动入库
RAG文档/片段索引；用查询和retriever找到支持材料，再供生成外部知识库可单独更新不必改模型参数，可保留来源；检索与文档质量另成瓶颈
KV cache本轮历史token在各层形成的Key/Value或压缩表示请求/会话内，或有效前缀复用不增加学到的固定参数；内容由具体上下文动态产生
preserve_thinking把已生成的思考文本保留/回传进后续请求或模板显式对话历史，受上下文容量约束是上下文组织策略，不是权重存储，也不保证跨会话永久记忆
n-gram投机解码从已知序列重复模式提议接下来若干token，目标模型验证本次生成的加速状态同样叫n-gram，却是起草token的加速算法，不是增加训练记忆表

RAG的经典形式包含参数生成器和外部检索索引；KV分页则处理动态运行时缓存；两者的来源与可更新性不同。RAG原论文 ↗、PagedAttention ↗

Qwen官方模型卡解释preserve_thinking保留历史reasoning blocks供后续输入；可能减少重想、改善前缀缓存复用，也会保留更多上下文。它不是把思考写进Engram，更不意味着节省所有情景的token。DeepSeek官方工具思考接口则要求按其协议回传reasoning_content，不能把一个平台的参数名和默认行为泛化到另一平台。Qwen模型卡 ↗、DeepSeek工具思考协议 ↗

2026的重要性，应放在正确历史线上

  • 稀疏专家与路由不是2026新概念；2017稀疏门控MoE、2021 Switch、2024 DeepSeekMoE/V3已提供关键基础。2026值得研究的是每个模型如何组合、扩规模、训稳，并让它在实际硬件上划算。
  • hash embedding也不是2026首创，2017已有明确论文。Google在2025 Gemma3n已探索PLE等参数分层/卸载；不能因为今天叫“条件记忆”，就把查表、分层存储的一切都算新发明。2017 Hash Embeddings ↗、Google Gemma3n开发说明 ↗
  • Engram的重要推进是把局部参数记忆作为与MoE互补的容量轴，连同门控、分配和系统实验一起研究；Qwen进一步在其配方中做位置/容量/准确率消融，并接入混合注意力、残差和优化器整体设计。这不是“又多加了一张表，所以逻辑能力无限提高”。
  • 最该问的反事实：在总参数、训练FLOPs、训练token、后训练、推理预算、硬件与质量门槛明确后，这种容量分配是否仍优于把同样资源给更多专家、更宽主干或更长训练？等FLOPs也不等于等美元成本，后者还包含存储/通信与利用率。
