主时间线

2026-01-27，官方发布 / 产品与 API 可用 · Kimi K2.5

已核实变化
在 K2-Base 上继续预训练约 15T 图文混合 token；原生视觉、多模态编程，统一 Instant / Thinking。模型卡：1T 总参、32B 激活、256K 上下文、MLA、400M MoonViT。Agent Swarm Beta 是同一模型的编排形态，不是四个新底座。

关键是视觉输入进入代码与工具闭环，而非只增大聊天知识。15T 是续训 token，不是参数；1T 总参不代表每 token 都激活 1T。视觉生成示例部分使用外部图像生成工具，不应宣传为底座原生图片生成。

已核实变化

研究解读与边界
是复现与部署的重要细节，但不是 K2.6 式新代际；错误模板可以造成第三方服务能力偏差。

2026-02-02，论文 v1；2026-02-09，独立系统博客 · K2.5 报告 / Agent Swarm

已核实变化
PARL 训练协调者动态拆任务；最多 100 子 Agent、1,500 步协调调用，厂商宽搜索任务最高约 4.5 倍墙钟加速。
研究解读与边界
并行降低关键路径延迟，不等于总 token 或总费用降低；适合可分解任务，串行依赖任务收益有限。2 月博客不能再次算一个新模型。

2026-04-20，官方发布 / API / 权重开放 · Kimi K2.6

已核实变化
仍为 1T / 32B / 256K / MLA；重点转向长程工程、指令遵循、工具调用与主动后台 Agent。Swarm 产品扩展到 300 子 Agent、4,000 协调步骤。
研究解读与边界
主要是同一规模下的任务执行可靠性，而非参数跃迁；12—13 小时工程演示和 5 天后台运行是挑选案例，不是所有任务稳定运行保证。

2026-06-12，官方 Code 发布记录；6 月 API 上线 · Kimi K2.7 Code

已核实变化

研究解读与边界
与 K3 并行的成本 / 专精路线，不应按编号把它当 K3 后继。约 30% 是思考 token，不是总 token、延迟或总任务费一律减少 30%。

2026-07-16，产品 / API 首发；07-27，HF 初始提交（含权重分片） · Kimi K3

已核实变化
2.8T 总参、104B 激活、1M 上下文；KDA + Gated MLA 混合注意力、Attention Residuals、Stable LatentMoE，896 专家选 16。原生视觉与长程编程 / 知识工作。
研究解读与边界
相较 K2 的确有架构与规模变化。稀疏激活降低计算，但全部权重仍要存储；1M 窗口不等于同样长的有效理解或免费缓存。厂商约 2.5 倍 scaling efficiency 不是 API 推理吞吐提升 2.5 倍。

2026-09-11，Kimi Code 预览模型上线 · K2.8 Preview

已核实变化

2026-10-23，Code 上线；官方研究目录标 10-24；11-02，HF 初始提交（含权重分片） · Kimi K3.1 Pro / Highspeed

已核实变化

研究解读与边界
不是完全重新预训练的 K4。10-23 / 24 是不同官方渠道记录，不擅自确定为时区原因；权重公告承诺最迟 11-04，HF 记录显示含权重分片的初始提交在 11-02；尚不能仅凭提交记录确定仓库当时公开可下载的时刻。Highspeed 不单算新底座。

同条件改进与不可比陷阱

  1. K2.6 相对 K2.5：官方模型卡给 SWE-Bench Verified 76.8 → 80.2（+3.4 个百分点），SWE-Bench Pro 50.7 → 58.6（+7.9 个百分点），Terminal-Bench 2.0 50.8 → 66.7（+15.9 个百分点）。不要把不同测试集揉成“编程提升 15.9%”。SWE 测试使用自建 SWE-agent 变体，报告对编程任务平均 10 次运行，Terminal-Bench 用 Terminus-2；不同 harness、token 预算与重试次数会改变成绩。来源：模型卡 ↗、评测脚注 ↗。
  2. K2.7 Code 相对 K2.6：模型卡给 Kimi Code Bench v2 50.9 → 62.0、Program Bench 48.3 → 53.6、MCPMark Verified 72.8 → 81.1；Code 更新日志的 +10.4%、+11.4% 是相对增幅，分别对应 +5.3、+8.3 个百分点，不是同一概念。前者为内部评测，后两者也须看任务集、工具与采样。来源：K2.7 模型卡 ↗。
  3. K3.1 Pro：官方博客内部长程 Code Bench 3.0：K3 55.95 → 61.2；内部 Kimi Hallu Bench Hard 的逐主张错误率 23.4% → 8.3%。这是刻意挑选高难事实问题的 stress test，不能说“日常错误率只剩 8.3%”。对外榜单中 HLE-with-tools 与 HLE-no-tools、最高推理档与默认档、最大输出与墙钟预算都须分开。Terminal-Bench 4.0 的 65.7 不可直接对比早代 2.0 的 66.7。来源：K3.1 技术博客与方法脚注 ↗。
  4. “长时间运行”与“有效工作”不同：调用更多工具、连续运行更多小时、300 个 Agent，均不直接等于正确率、产出质量或经济性。应跟踪同一任务成功率、人工复核 / 返工时间、总工具费用、成功任务成本及 P95 完成时长。此项为研究推断。
  5. 开放权重与许可证：K2.5/2.6/2.7 模型卡标 modified-MIT；K3 与 K3.1 是自定义 Kimi License。K3.1 许可证对达到收入门槛的 MaaS 经营者有另签协议要求，对超大产品有署名条件，内部使用和官方/认证推理伙伴通道另有豁免。不能笼统写“全系列无条件 MIT 开源”。K3.1 License 原文 ↗。

机制解读与批判性结论

  1. 3.5 的核心是训练/架构基础改变，3.6/3.7 重心转到把任务跑完。 GDN 把历史压到状态中，隔层全注意力补精确访问，再结合 MoE 降每 token 计算；因此“总参数大、激活少”可以同时出现。但少激活不等于同等比例少显存：权重仍要存储/分布，专家路由、通信和 KV 状态都要算。3.6 的历史思考保留影响多轮任务状态，3.7 的环境扩展影响泛化范围，二者不是单纯继续堆预训练参数。
  1. Flash-Next 值得比 Max 的一个排行榜更深入地研究。 GDN 压缩历史、QSA 以小块选信息，减的是长序列注意力和索引成本；Gated Residual 改信息流；N-gram 表给局部模式记忆且可放主存，Muon 与架构一起改训练稳定性和超参。论文明确指出更低 loss 不总意味着更高下游分数，n-gram 词表扩大后精度会饱和。该事实直接反驳“更多容量必定更好”的简单宣传。
  1. 成本宣传不能直接翻译成终端用户收益。 论文“约 1/9”比较的是训练 FLOPs，并伴随更少训练 token/激活参数，不是每次用户调用便宜九倍。官方 8.6 倍 prefill 吞吐采用 1M 上下文和 90% prefix-cache 命中的特定实验；短输入、低命中、通信瓶颈或低并发不应照搬。真实研究指标应为同硬件/精度/并发下的 TTFT、tokens/s、峰值显存、工具费、重试率与每成功任务总成本。
  1. 长上下文、长期执行、永久记忆不同。 1M 是一次请求可接收的窗口上限，preserve_thinking 是多轮协议保留中间状态；框架的存储/压缩/检索才构成长时记忆系统。单次 35 小时 demo 或一套自动演进仓库不能识别通用成功率，必须有任务样本分母、超时/人工介入统计与失败类型。
  1. 排行榜不能当成控制变量实验。 3.8 大卡表头列的是 Qwen3.8-Max，而非保证所有分数由开放纯文本 2.4T 同设置复现；Terminal Bench 比较中其他模型取各自最好公开 harness，DeepSWE 取多个 harness 最优；若引入代码解释器、搜索、工具以及“改正过的题目集”，必须列设置。跨发布文章不同 AIME 集、SWE harness、输出预算/重复采样不可直接算提升百分比。
  1. API 品牌与模型权重必须拆开。 Plus/Max/Flash 是服务产品档，不是稳定的参数尺寸；alias 可能更新，snapshot 才固定一个版本；地区开通晚数周不是底座又发布一次。3.8 开权重版本纯文本且自定义许可证，是本次最容易被二手新闻写错的两点。Qwen4 此刻只有限时 Preview，Flash-Next 是架构先行材料，二者不证明完整第四代开放。

推荐研究判断

  1. 2026的主线至少有四个互相不同的变量：底座参数与模态；后训练与交互环境；注意力/KV/解码效率；产品harness与工具编排。不能把四类进展揉成一句“智力提升”。
  2. 1M只是可接收上下文上限；需测任务检索/约束保持、并发KV内存、TTFT和价格，不等于读懂100万token。
  3. 比价应看“完成且验收通过一次任务的总成本”：输入/输出/缓存、工具调用、重试、超时、人类复核；TPS与token单价分别很低仍可能高总成本。
  4. 厂商自建金融/研究基准（FinStepBench、BankerToolBench等）可揭示目标任务，不足以证明真实投资决策收益；重点看数据污染、隐藏测试、可重算与来源追溯。
  5. 可靠性修复事件应与能力发布同等重视：小米官方工具重复反思比一张SOTA雷达图更能说明RL奖励盲点与harness依赖。
