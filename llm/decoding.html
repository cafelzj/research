MTP：训练监督与草稿模块

文本MTP：训练目标与推理解码要分别理解

传统NTP训练：“看到前缀，猜下一个token”。DeepSeek-V3式MTP增加串联的小预测模块，在训练时把前一级隐藏状态与对应未来token的embedding结合，预测再下一个token，增加监督密度；它不是若干互不相干的头同时瞎猜未来。共享embedding/输出head，新增的是预测模块等成本。DeepSeek-V3 §2.2 ↗、NVIDIA Megatron实现说明 ↗

训练：主干h_i预测t_(i+1)
      h_i + 真值embedding(t_(i+1)) → MTP模块 → 预测t_(i+2)

推理：主干先产生t_(i+1)
      h_i + 草稿embedding(t_(i+1)) → 小模块 → 提议后续token
      由目标大模型验收草稿，才提交输出

训练时用真值是teacher forcing；推理时还没知道未来真值，要用已生成草稿。MTP训练可改善主干表征；推理也可以丢掉额外模块正常单token生成，或把它作为投机draft。MTP不自动等于已启用投机加速，更不保证“预测3个就快3倍”。

投机解码：大模型一次并行验算多个条件分布

查看结构连接（文字版）
  • 已确认前缀 → 小draft提议一串token x1 x2 x3 x4
  • 小draft提议一串token x1 x2 x3 x4 → 目标模型带因果mask 一次算各位置条件分布
  • 目标模型带因果mask 一次算各位置条件分布 → 从左到右接受检验
  • 从左到右接受检验 → 接受连续前缀x1 x2
  • 从左到右接受检验 → x3第一次拒绝 丢弃x3及其后所有草稿
  • x3第一次拒绝 丢弃x3及其后所有草稿 → 从残差分布抽纠正token
  • 接受连续前缀x1 x2 → 提交已接受前缀+纠正token
  • 从残差分布抽纠正token → 提交已接受前缀+纠正token
  • 提交已接受前缀+纠正token → 已确认前缀

这里并行的是“已给定这条草稿前缀，各位置该取什么概率”的验证，类似训练时teacher forcing；目标模型仍保持因果mask，不会偷看未来草稿。若第三个失败，第四个即使孤立看起来很好也不能保留，因为它是在错误第三个的条件下提出的。

设目标条件分布p、实际draft条件分布q，候选x~q：

  • 接受概率 min(1,p(x)/q(x))。
  • 第一个拒绝处从 r(v) ∝ max(p(v)-q(v),0) 抽纠正token。
  • 全部接受时再从目标模型抽一个bonus token。

这套拒绝校正使最终采样分布仍为目标p。它不保证用相同随机种子逐字得到同一条样本；随机数消耗路径已变。“无损”是相对于指定目标采样分布，不是声称目标模型本来正确、或对量化后模型也恢复原高精度分布。原始算法及证明 ↗、论文PDF Algorithm1/AppendixA ↗

条件不能省：q要是实际产生候选的概率，p要对应真实目标的temperature/top-k/top-p等采样规则；KV状态、attention mask、接受后的前缀一致；adaptive调度不能看完候选再挑有利的输出路径而不修正选择偏差。贪心验证另有“逐位匹配目标argmax”的确定性规则，不能拿它代替随机采样拒绝校正。

算术教学：假设每一位置条件接受率都为常数a，最多draft g个，则每轮包括纠正/bonus的期望输出约为 1+a+…+a^g。这是假设模型，不是生产测量：

假设g=4时每轮期望输出草稿4步总耗时0.4，目标验收耗时1相对逐token耗时1的加速
a=0.83.3616每轮1.42.40倍
a=0.21.2496每轮1.40.89倍，反而更慢

现实中的目标验收并非固定耗时1。批量/并发增大、长上下文KV访问、MoE专家通信、候选数量、设备算术强度都会改变耗时。算得多的FLOPs可能因权重复用而更快，但当GPU已经算力饱和，多验无用token会挤占其他请求容量；单用户TPS与整机吞吐不可混看。

DSpark：草稿内部补依赖，验收长度适应负载

DSpark是2026-07论文披露的draft架构+调度方案，不是给DeepSeek底座换一个聊天人格，也不是新基础模型。它针对两个瓶颈：完全自回归draft串行太慢；完全并行draft各位置不知道此前究竟采到了哪个词，后缀接受率掉得快。

查看结构连接（文字版）
  • 目标模型上下文特征 + anchor token → 较重的并行draft backbone 一次算多个位置
  • 较重的并行draft backbone 一次算多个位置 → 很轻的顺序校正头 引入已采样前缀依赖
  • 很轻的顺序校正头 引入已采样前缀依赖 → 草稿及其真实条件概率
  • 较重的并行draft backbone 一次算多个位置 → confidence head
  • confidence head → 硬件/当前负载感知 选择验证前缀长度
  • 草稿及其真实条件概率 → 硬件/当前负载感知 选择验证前缀长度
  • 硬件/当前负载感知 选择验证前缀长度 → 目标模型并行验证 标准拒绝校正

代码中的VanillaMarkov以“前一个token低秩embedding→词表偏置”修正并行logits；GatedMarkovHead再根据当前隐藏状态门控；RNNHead可携带块内前缀状态。然后按真实校正后的softmax逐个采样，因而还能提供拒绝采样所需的确切q。这不是把“of course/no problem”的第二个词独立乱配成“of problem”。官方顺序头实现 ↗

confidence是预计“会被目标接受”的概率，不是答案事实正确率。单层AcceptRatePredictor接隐藏状态及可选前一个token特征；调度器再结合累计前缀存活概率与实测硬件吞吐曲线决定验多少。置信度校准差会损失性能，但只要仍执行正确验收、保持调度条件，不应让置信度直接取代目标模型批准。预测头及模型实现 ↗、库集成说明 ↗

无损前提里最容易被忽略的是非预见性：是否把位置k纳入验证，要由采样该位置前可见的信息决定。若看完未来候选后再全局挑一段最划算的前缀，就可能选择性保留某些词。DSpark附录给出目标(0.7,0.3)被偏成(0.85,0.15)的反例；顺序早停避免这种回看偏差。DSpark §3.2、AppendixA ↗

作者实测称相同吞吐约束下用户生成速度较MTP-1快60%—85%，限定在其V4-preview、生产engine和流量条件。论文离线“每轮接受长度”的表明确包括bonus，不能与不含bonus的指标直接比。置信度调度只减少目标验收浪费，低接受请求已经付出的整块draft成本仍拿不回来。DSpark §4、5及限制 ↗

量化、部署与性能验收

量化改变权重、激活或缓存采用的数值格式；QAT 在训练中适应量化误差。要分别记录位宽、缩放元数据、异常值处理、内核与硬件支持，不能把 4-bit 理想裸字节量当作真实部署总显存。

Kimi K3.1 公开 MXFP4 权重 / MXFP8 激活；V4.1 的 FP4 KV 则作用于缓存，属于不同对象。参考代码中的量化后反量化模拟，也不能直接验证生产内核的存储和速度。K3.1 模型卡 ↗、V4.1 数值与部署说明 ↗

Muon 是训练优化器，Slime 是强化学习基础设施，历史思考保留是上下文协议，Swarm 是编排形态。它们可以显著改善模型或产品，但应单独说明收益来源。

成为研究员应问的验收问题

  1. 多模态：输入是向量级跨模态、OCR文字中转，还是工具系统拼接？细粒度证据何时被压缩掉？
  2. 语音：首包统计从什么时点开始？包含网络/用户停顿检测/客户端缓冲吗？是否同时提供RTF、并发和自然度？
  3. OCR：有没有阅读顺序、表格/公式、小字和各文档类别结果？重复率能否替代ground-truth准确率？
  4. 投机：报告的是draft长度、接受长度还是含bonus总输出？只给离线acceptance还是有真实负载下延迟/吞吐曲线？
  5. 无损：验证是贪心匹配还是随机拒绝采样？是否保留目标sampler、条件概率与调度非预见性？“无损”相对哪个精度/哪个checkpoint？
  6. 系统：开源的是权重、draft模块、训练代码还是harness？demo中的跨应用行为是否被误写进底座架构？
